# OPC UA 订阅信号等待

新增流程块 `opcua_wait` 和 Node-RED `machine-opcua_wait`，使用已锁定 asyncua 2.1.0，不增加依赖。典型流程为：等待 OPC UA 请求 → 相机采集 → 检测 → 写回结果。配置采用表单，通知明细及变量采用表格。接口依据：[官方 GitHub 仓库](https://github.com/FreeOpcUa/opcua-asyncio)、[订阅示例](https://github.com/FreeOpcUa/opcua-asyncio/blob/master/examples/client-subscription.py)；开发分支示例不替代本项目固定版本。

## 语义

- 一次调用连接一个服务器、订阅一个节点，在同一会话中等待；结束时删除订阅并断开。认证、安全策略、证书和命名空间 URI 沿用现有 OPC UA 读写配置。
- 条件支持数值等于/不等于/大小比较和 Boolean 为是/为否。仅接受良好质量的数值或开关标量；不隐式转换文本、数组或大于 JavaScript 安全整数范围的数值。密码仍从服务器环境变量读取，不放入工程。
- “条件成立”可在首个良好通知成立时触发。“不成立→成立”和“成立→不成立”必须先收到相应基线，再收到转换；初始值本身不是新边沿。每次调用、包括连续检测每轮，重新建立基线，不缓存跨轮事件。
- 等待超时为 100–600000 ms，从适配器连接前计时，不含 Python 启动；通信超时为 100–10000 ms。请求发布/采样间隔为 20–10000 ms，服务端可能修订实际间隔，界面显示的是请求值。
- 默认条件超时报错停止；选择继续时输出 `triggered=false`、`timedOut=true`，必须接条件节点处理，不能直接继续采集。继续前只读确认连接与节点质量；这个迟到读取不会作为触发或替代最后通知。
- 无有效初始通知、Bad/Uncertain 质量、断线、类型/协议错误，以及检测到的服务端或客户端通知队列溢出均失败，不伪装成普通条件超时。只读等待不写请求复位或应答位，也不自动重连/重试。

## 输出与边界

输出是否触发、首次/末次通知值、最后条件、已处理通知数、类型、质量、时间及最近 100 条通知表。超过 100 条历史明细标记截断，不改变边沿判定；客户端通知队列和服务端请求队列各为 100。发现队列溢出直接失败；不宣称发现所有设备或网络层的遗漏。

等待期间锁定本平台同主机/端口的通信端点，其他平台读写会被拒绝；设备和外部客户端仍可更新值。停止作业、连续检测或 Node-RED 关闭会中止等待进程，下游不执行，变量按既有事务回滚。设备上的先前写入不能回滚。

这是有界的软件订阅等待，**不是永久后台订阅、自动重连、多节点队列或无遗漏硬件触发**。服务端采样/发布间隔之间的短脉冲、两轮未订阅期间的变化可能遗漏。Good 状态也不证明数据足够新；来源时间戳只用于展示，没有额外的新鲜度门限。现场应使用保持请求/工件序号/确认应答，精确曝光同步使用设备硬件触发。连续电平模式会在请求保持成立时逐轮重复检测。

## 验证

`npm run test:opcua-wait` 包括本机真实 OPC UA 协议、初始基线/上升下降/超时、质量/数组/安全数值/队列限制、迟到确认不触发、会话清理、流程/相机/真实 OpenCV、三级变量/回滚/互斥/取消、连续轮次、自动表单、HTTP 保存/历史/重启和实际部署 Node-RED 节点。既有 `tests/test_opcua.py` 另覆盖签名加密/用户名认证的等待及错误密码不泄漏。

工作台三个演示为订阅后采图检测、初始成立但无新边沿的超时分支、超时停止。它们先将本机模拟计数写为 0，保持可重复运行。只操作本机模拟服务器，不代表真实 PLC、现场时序、长期可靠性或 Linux/新增界面可视验收。冻结的 0.3.0 开发候选 2 不包含本次新增功能。
