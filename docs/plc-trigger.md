# PLC 信号等待与触发

`modbus_wait` 使用已锁定的 PyModbus 3.16.1，实现 Modbus TCP / 串口 RTU 的单值轮询。工作台“流程控制 → 等待 PLC 信号”、Node-RED `machine-modbus_wait` 和服务器连续检测共用同一个适配器。配置用表单，输出用结果表及变量绑定；不要求用户编辑 JSON。

## 使用

典型流程：数据源 → 等待 PLC 信号 → 相机采集 → 检测 → 结果写回。采集节点放在等待之后，以免使用触发前图像。节点只读，不自动清除 PLC 请求位或写应答位。真实设备的请求保持、完成应答及故障复位需在工程和 PLC 程序中明确设计。

| 参数 | 含义 |
|---|---|
| 连接方式 | 本机模拟、TCP 或 RTU；地址为从 0 开始的协议地址 |
| 数据区域 | 保持寄存器、输入寄存器、线圈、离散输入 |
| 数值类型/字节序/字序 | 沿用读写模块；一次读取一个解码值，float64 占 4 个寄存器 |
| 信号条件 | 寄存器使用数值相等/不等/大小比较；开关使用“为是/为否” |
| 触发方式 | 条件成立；条件由不成立变为成立；条件由成立变为不成立 |
| 采样间隔 | 20–10000 ms；每次读取完成后再等待该时间，不是恒定频率 |
| 连续采样稳定时间 | 0–60000 ms；所需条件在连续采样中保持该时长，必须小于等待超时 |
| 等待超时 | 100–600000 ms；从适配器开始连接计时，包含连接和读取，不含 Python 进程启动 |
| 通信超时 | 单次连接/收取响应的超时，100–10000 ms |
| 超时处理 | 默认报错停止；也可返回 `triggered=false`，再用条件模块选择超时处理分支 |

“成立→不成立”判断的是所配置条件。例如条件为“值 > 10”，值从 20 变为 5 可触发该模式。每次调用（包括连续检测每一轮）都重新建立基线：边沿模式必须先读到反向状态，再读到目标状态；初始值已经是目标状态时不会直接触发。稳定时间中出现反向采样会重新计时。

输出包含是否触发、首次采样值、最后采样值、最后条件状态、采样次数、实际等待耗时和采集时间。`passed` 等同于是否触发，不是视觉质量判定。超时后的有效响应只保留为最后采样值，不能触发检测。只有等待条件超时可返回“未触发”；断线、设备异常码、响应长度错误和非有限数值始终失败。程序关闭连接，不执行自动恢复循环或失败重试。

## 运行与边界

- 等待期间在同一个 Python 进程、同一个客户端连接中顺序轮询；复用现有端点锁，等待结束/取消前不允许平台其他节点使用相同端点。外部 PLC 自身可以改变其寄存器状态。
- 工作台停止、连续检测停止、Node-RED 关闭/重新部署节点会终止等待进程。取消不执行下游，流程变量按原有事务回滚；先前发生的设备外部写入不能回滚。
- 在途通信可能晚于等待超时返回；程序不会接受迟到响应作为触发。外层进程看门狗上限为等待超时 + 2 倍通信超时 + 2500 ms；点击停止通过结束进程取消，不等待该上限。
- 这是采样式软件触发，不能保证捕获采样之间的短脉冲，稳定时间也不证明两次采样之间的电平未变化。连续流程执行期间未采样的变化不会缓存。需要无遗漏触发时，应让 PLC 保持请求直至应答、使用工件序号/队列，或采用相机硬件触发与专门采集通道。
- 电平模式连续检测时，只要信号仍成立，每轮会再次检测；边沿模式每轮重新等待完整转换。未实现跨轮边沿缓存、统一请求应答状态机及设备断线重连。

## 验证与演示

`npm run test:industrial` 包含原 Modbus 回归、新增 9 项 Python 检测/协议测试及 6 项运行时测试，另验证 HTTP、工程保存和真实 Node-RED 节点链路。覆盖上升/下降转换、初始高电平、采样抖动、四种地址区域、浮点端序、迟到响应、超时分支、失败回滚、端点互斥、连续轮次和在途取消。TCP 测试使用本机真实协议服务器，RTU 采用现有串口参数与编码适配，尚未用实际 RTU PLC 验证本触发块。

工作台演示案例新增：

1. **PLC 信号 → 相机采集 → 检测**：模拟就绪值连续采样稳定 150 ms 后采图，真实 OpenCV 检测数量为 3。
2. **PLC 边沿等待 → 超时分支**：初始就绪值不构成新边沿，500 ms 后走超时分支。
3. **PLC 等待超时 → 停止检测**：不满足条件时停止，后续视觉节点不执行。

当前通过 Windows 本机协议/模拟相机验证，真实 PLC、RTU 触发及 Linux 运行仍待现场验收。已有 0.1.0 封存发布包未包含本轮更新。
